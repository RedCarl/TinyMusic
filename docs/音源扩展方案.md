# 音源扩展方案：从「单平台匿名」到「多源聚合 + 兜底」

> 调研对象：
> - [cdyUuu/lx-music-xinghai-source](https://github.com/cdyUuu/lx-music-xinghai-source)（星海音乐源）
> - [pdone/lx-music-source](https://github.com/pdone/lx-music-source)（洛雪音源索引 + 每日健康检查）
>
> 结论基于 2026-11-06 的实测（本机网络、当前接口行为）。第三方接口会变，数据只代表当日。

---

## 0. 结论先行

**这两个项目都不能作为「音源」直接接进 TinyMusic。** 它们是给 LX Music 用的插件，
运行在 LX 的 `globalThis.lx` 宿主里，只回答「这首歌的播放地址」，连搜索都不提供。
它们背后的可用地址，一半是私有网关（带 apikey / 签名 / 混淆），不对外承诺稳定。

能落地、且真正能提高「播放成功率」的是三件事，按收益排序：

| 优先级 | 事项 | 收益 | 工作量 |
|---|---|---|---|
| **P0** | 播放链路工程加固：真实时长校验、音质回填、失败自动重取、代理回源 | 立竿见影，修掉「标 320 实为 128」「片段判可用」「一次失败就判死」 | 1–2 天 |
| **P1** | 新增网易云平台（匿名搜索/取流/歌词/专辑 + 可选 cookie） | 曲库明显变丰富，长尾覆盖提升 | 3–5 天 |
| **P2** | 跨源兜底：酷我失败 → 按标题/歌手/时长匹配网易云 | 失败曲目的「能播」比例提升 | 1–2 天 |
| **P3** | 可插拔「音源网关」配置（用户自备） | 有账号/有自建服务的用户可解锁高音质与 VIP | 2–3 天 |
| P4（不建议先做） | 内嵌 JS 运行时跑 LX 脚本 | 覆盖面最大，但工程/安全/稳定性成本远高于收益 | 1–2 周 |

一句话：**先修链路，再加平台，最后做兜底；不要一开始就想着「把星海搬进来」。**

## 1. 两个参考项目到底是什么

### 1.1 星海音乐源（xinghai）

形态是一个 `.js` 文件，头部声明：

```js
const { EVENT_NAMES, request, on, send, env } = globalThis.lx;
on(EVENT_NAMES.request, async ({ action, source, info }) => {
  if (action === 'musicUrl') return fetchMusicUrl(source, info.musicInfo, info.type);
  // 另外只处理 lyric / pic
});
```

也就是说：

- **它不提供搜索、专辑、歌手、歌单**。这些由 LX Music 客户端自己完成，
  插件只负责「给我 URL」。
- 它依赖宿主提供 `request`（网络代理）、`send`/`on`（事件总线）、`env`。
  脱离 LX 运行时，这个脚本什么都做不了。

它内部拼了四条链路：

| 链路 | 地址 | 是否需要凭据 | 备注 |
|---|---|---|---|
| 自有后端 | `https://yy.zddyr.top/lx/api/` | 需要 `X-Token`（客户端生成）| 实测伪造 token 返回 403 |
| ChKSz | `https://api.chksz.com/api/163_music`、`/api/qq_music` | 需要 apikey | 代码里 apikey 留空，默认不启用 |
| GDAPI | `https://music-api.gdstudio.xyz/api.php` | 无 | 实测**目前只支持 netease** |
| 酷我解密中转 | 用户自建 `kuwo-music-relay` | 自建服务 | 用于解密 `.mflac` / `.mgg` |

**实测（2026-11-06）：**

```text
GET https://yy.zddyr.top/lx/api/?source=netease&...&songmid=185809
  X-Token: <按脚本逻辑自行生成>        → 403 {"msg":"令牌无效或已过期，请使用官方版本"}
  不带 X-Token                        → 400 / 502（取址失败）
GET https://music-api.gdstudio.xyz/api.php?types=search&source=tencent|kugou|migu|kuwo
                                       → {"detail":"Value of `source` is not supported."}
GET https://music-api.gdstudio.xyz/api.php?types=url&source=netease&id=3404293607&br=320
                                       → 200，返回可用的网易 CDN 直链
```

它的后端 `auth` 字段里还带 `tk_tier`、`tk_mismatch`、`client_broken` 这类风控信息，
说明这是一个**按客户端版本/令牌分级放行**的私有服务，不适合作为桌面客户端的依赖。

**结论：星海能借鉴的是「按平台分优先级的取址链」，不是它的地址。**

### 1.2 pdone/lx-music-source

这是一个**音源索引仓库**，README 里列了 16 个 LX 音源（长青、六音、Fish、聚合、星海、玉宁熙……），
每天 01:00 跑一次健康检查（当前覆盖 15 个），把结果发到 `health-status` 分支。

2026-11-05 的健康快照：**15 个音源**，**69 个上游 host**：

| 状态 | 数量 |
|---|---|
| 可用 | 37 |
| 异常 | 18 |
| 失效 | 14 |

其中不少脚本是混淆过的，并且内置了私有网关和密钥，例如「独家音源」：

```js
globalThis['SERVER_SCRIPT_CONFIG'] = {
  apiUrl: "https://88.lxmusic.xn--fiqs8s",
  apiKey: "lxmusic",
  signSalt: "LxSrv@2026#Sig",
  fingerprint: "42bc92aaf1a30247e40eab9523ca0713"
};
```

这类「服务端下发配置」的脚本，密钥会轮换、网关会挂、脚本会改名，**不是稳定 API**。

它也验证了一件事：**近半数上游随时不可用，所以任何单源方案都不可靠，
必须做「多源池 + 健康探测 + 快速失败」。**

## 2. 我们现在的链路与真实瓶颈

### 2.1 现有架构

```
前端 player.startAt()
  → api.playerOpen(provider, id, quality)      src/lib/api.ts
  → tauri command player_open                  src-tauri/src/lib.rs:449
  → MusicProvider::resolve()                  core/src/model.rs
  → StreamProxy::register(url)                core/src/proxy.rs
  → http://127.0.0.1:{port}/stream/{token}    → CDN
```

`MusicProvider` trait 已经抽象好了平台维度（`core/src/model.rs`），
`registry()` 里加一行就能注册新平台（`core/src/providers/mod.rs`）。
**平台层不难扩，难的是「可用性」和「前端假设」。**

### 2.2 实测基线：酷我热门曲其实已经很高

用 `core` 的 live 测试对 12 个关键词、每个取前 2 首，共 24 首，在 320k 档取流：

```text
=== kuwo@320k: 24/24 ===
（21 首标记 Super、3 首标记 High；23 首拿到 3.6MB–12.9MB 的完整音频，
  1 首 48 秒短曲只有 777KB，却仍标成 Super —— 见下表「音质标签失真」）
```

`yl_res_manage` 资源管理链路确实解决了 VIP 曲的完整取流（和 README 的结论一致）。
**所以「播不出来」不是普遍现象**，问题集中在少数具体环节：

| 问题 | 证据 | 影响 |
|---|---|---|
| **时长校验是死代码** | `resolve()` 调 `resolve_with_fallback(id, q, 0)`（`core/src/providers/kuwo/mod.rs:807`），`is_placeholder` 的第三级「按字节/时长估算」永远算不了 | 片段可能被判为可用；也无法判断真实音质 |
| **音质标签可能失真** | 实测 `200677874` 请求 320k，`res_manage` 返回 777,949 字节；该曲真实时长 48s，按 128k 算正好 ≈48.6s，却仍标成 `Super` | 用户看到「320k」，实际听的是 128k |
| **失败即判死** | `player.svelte.ts:361` 捕获取流异常后直接 `markUnavailable(track)`，不重试 | 一次网络抖动/一次占位，整首就变灰 |
| **无跨源兜底** | 只有 `kuwo` 一个 provider | 酷我没有/取不到的歌，直接结束 |
| **前端写死平台** | `src/routes/Search.svelte:78/96/126`、`src/routes/Account.svelte`、`src/lib/account.svelte.ts` 都硬编码 `'kuwo'` | 加平台不是「后端加一行」就完事 |
| **缓存 24h + 代理 token 5min** | `resolve_cache` 24h（`kuwo/mod.rs:179`）、`TOKEN_TTL` 5min（`proxy.rs:21`） | CDN 链接若提前失效，会持续失败到缓存过期 |

好消息是：**这些都不是协议层的大改，是工程层的修补。**

## 3. 各平台匿名能力实测（2026-11-06）

| 平台 | 搜索 | 取流 | 歌词/专辑 | 备注 | 可接入性 |
|---|---|---|---|---|---|
| 酷我（现有） | ✅ | ✅ 24/24 @320k | ✅ | `res_manage` 链路稳定 | 已接入 |
| 网易云 | ✅ `interface.music.163.com/api/search/get/web` | ⚠️ 热门 10 首里 3 首拿到 320k 完整音频，其余 `-110` | ✅ 歌词、专辑 | 免费曲大多可播；VIP/版权曲需登录 cookie | **高** |
| GDAPI | ✅ 仅 netease | ✅ 有时效直链 | — | 第三方代理，只能补网易云 | 中 |
| QQ 音乐 | ✅ `c.y.qq.com/soso/fcgi-bin/client_search_cp` | ❌ vkey `purl` 为空 | — | 需要签名/登录 | 低（先不做） |
| 酷狗 | ✅ `songsearch.kugou.com/song_search_v2` | ❌ `play/getdata` 返回 30020 | — | 需要 dfid/mid 签名 | 低 |
| 咪咕 | ✅ `c.musicapp.migu.cn/MIGUM2.0/v1.0/content/search_all.do` | ❓ `listenSong` 需要 `copyrightId` + `toneFlag` 组合 | — | 待验证 | 中 |
| 星海后端 | — | ❌ 403（令牌校验） | — | 私有服务 | 不可依赖 |

网易云的匿名取流实测细节（10 首热门）：

```text
晴天/消愁/日不落 …            → 200, br=320000, size=9–11MB（完整）
孤勇者/光年之外/江南/演员 …    → -110（无版权/需登录）
带 Cookie: os=pc; appver=2.9.7 → 部分变 200，但返回 128k、size=481KB/720KB
                                 （同一错误文件被复用于多首歌，不能当可用）
```

**结论：匿名能稳定补的是「网易云免费曲 + 部分可播版权曲」。
热门 VIP 曲的全覆盖，只能靠「用户自己的账号 cookie」或「用户自备网关」。**
这正好符合本项目「不内置登录、但留 cookie 逃生通道」的既有立场
（`MusicProvider::login_cookie` 已经存在）。

## 4. 方案

### P0 —— 播放可靠性加固（1–2 天，收益最大）

不改平台，只修链路。按顺序做：

**P0-1 把曲目时长传进取流逻辑**

```rust
// core/src/model.rs
async fn resolve(&self, id: &str, q: Quality, duration_sec: u32) -> Result<StreamInfo>;
```

调用方（`src-tauri/src/lib.rs` 的 `player_open` / `resolve` / 下载）都能拿到
`Track.duration_sec`，传进去即可。这样 `is_placeholder()` 的第三级判定才真正生效，
`res_manage` 的结果也能做同样的校验（目前完全没校验）。

**P0-2 真实音质回填**

`StreamInfo` 增加 `actual_kbps`；用 `bytes * 8 / duration` 估算（误差 ±10%），
超出目标档位 85% 才标 `Super`，否则降级标 `High`。UI 的音质徽标改成读这个值。
这样「标 320 听 128」的问题就消失了。

**P0-3 失败自动重取一次**

`player_open` 失败或代理返回 5xx 时，让 provider 清掉该曲的 `resolve_cache` 再试一次。
前端 `startAt` 的 `catch` 改成：

```ts
catch (e) {
  if (!retried) { retried = true; return startAt(i, fromSec); }
  markUnavailable(track);
}
```

一次重试能吃掉大部分「链接临时失效/抖一下」的失败。

**P0-4 代理层回源**

`StreamProxy` 目前对上游错误直接返回 502（`core/src/proxy.rs`）。
给它一个 `Arc<dyn Fn(String) -> Future<Option<String>>>` 回调解引用，
上游 403/404/5xx 时重新解析一次并重试。注意只重试一次，避免打转。

**P0-5 队列级连续失败保护**

连续 3 首失败时停下列表并提示「当前网络/音源异常」，
而不是一路 `ended → 下一首 → 失败` 刷屏。

**验收**：固定 50 首混合曲目（热门 + 长尾 + 现场/翻唱），
`成功率 ≥ 现状`、`片段误判 = 0`、`音质标注准确率 = 100%`。

---

### P1 —— 网易云成为第二平台（3–5 天）

新增 `core/src/providers/netease/mod.rs`，实现 `MusicProvider`：

| 能力 | 接口 | 状态 |
|---|---|---|
| 搜索 | `GET https://interface.music.163.com/api/search/get/web?s={kw}&type=1&limit={n}&offset={p*n}` | 实测可用 |
| 歌词 | `GET https://music.163.com/api/song/lyric?id={id}&lv=1&kv=1&tv=-1` | 实测可用 |
| 专辑 | `GET https://music.163.com/api/v1/album/{id}` | 实测可用 |
| 取流 | `GET https://interface.music.163.com/api/song/enhance/player/url?ids=[{id}]&br={128000/320000/999000}` | 实测部分可用 |
| 艺人 | 先用「搜索 + 按 artist id 归组」，与酷我同一策略 | 待验证 |
| 歌单 | `GET https://music.163.com/api/v6/playlist/detail?id={id}` | 待验证 |

质量映射：

| `Quality` | 请求参数 |
|---|---|
| Standard / High | `br=128000` |
| Super | `br=320000` |
| Lossless | `br=999000`（匿名多半 -110，需 cookie） |

**可选 cookie 登录**（强烈建议，直接决定 VIP 曲的成功率）：
用 trait 里已有的 `login_cookie`，解析 `MUSIC_U=...` 存入 `Session`，
之后所有取流请求带上 cookie。前端复用现有「账号」页的 cookie 输入框即可。

前端改动：

- `src/routes/Search.svelte`：平台选择器（酷我 / 网易 / 聚合），把写死的 `'kuwo'` 换成状态
- `src/lib/searchStore.svelte.ts`：缓存按 `provider` 分桶
- `src/lib/api.ts`：`types` 不变，`provider` 本来就是字符串
- 账号页：酷我保持现状，网易云加「cookie 登录」

**这一步完成后，「歌曲更丰富」的诉求基本就满足了**：两个平台的版权池互补，
搜索结果的多样性会明显好于单酷我。

### P2 —— 跨源兜底（1–2 天，依赖 P1）

目标：**酷我取不到（或只有片段）时，自动去网易云找同一首歌**。

```text
resolve(track):
  try kuwo.resolve(track)                      → 成功且时长校验通过 → 返回
  except / 片段:
    m = match_netease(track)                   → 置信度 ≥ 0.75 ?
      → netease.resolve(m.id, quality)
      → StreamInfo { url, provider: "netease", matched_from: "kuwo" }
```

匹配算法（纯本地，不发请求）：

```rust
fn normalize(s: &str) -> String   // 全角→半角、去括号内容、去 (Live)/(伴奏)/(Remix)、小写
fn score(a: &Track, b: &Track) -> f32 {
    let t = similarity(normalize(&a.title), normalize(&b.title));   // 权重 0.55
    let ar = artist_overlap(&a.artist, &b.artist);                  // 权重 0.30
    let du = duration_score(a.duration_sec, b.duration_sec);        // 权重 0.15，±8s 满分
    t * 0.55 + ar * 0.30 + du * 0.15
}
```

规则：

- 阈值 `0.75`；`0.60–0.75` 之间只在「专辑名一致」时放行
- 时长差 > 15s 直接拒绝（Live/剪辑版最容易串）
- 命中后 UI 标注「音源：网易云」，避免用户困惑
- 兜底结果**不写回**酷我的 `resolve_cache`，单独缓存，键带 `provider`

**预期收益**：酷我 24/24 的热门样本看不出变化，
但长尾/翻唱/独立音乐这一块才是兜底的目标——建议先用 P0 的 50 首基线里失败的那部分做验证。

---

### P3 —— 可插拔「音源网关」（2–3 天）

给高级用户一个口子：在设置里填自己的网关地址和 token，TinyMusic 在
「本地解析失败」之后调用它。这样：

- 有星海/ChKSz/自建服务凭据的用户，可以自己解锁高音质；
- 项目本身**不内置任何第三方私有密钥**，立场和现在一致；
- 网关挂了只影响兜底，不影响主链路。

我们定义自己的最小契约（不依赖 LX 的插件格式）：

```http
POST {base_url}/resolve
Authorization: Bearer {token}
Content-Type: application/json

{ "source": "kuwo", "id": "228908", "title": "晴天", "artist": "周杰伦",
  "duration_sec": 269, "quality": "super" }

200 { "url": "https://...", "quality": "super", "expires_at": 1793959999 }
4xx { "error": "..." }
```

设置页增加「测试连接」和「平台开关」；再加一个状态面板（学 pdone 的健康检查表：
最后成功时间、失败次数、当前状态），让用户知道哪个源今天不靠谱。

---

### P4 —— 内嵌 LX 脚本运行时（不建议先做）

理论方案：把 `rquickjs` 嵌进 Rust，polyfill `globalThis.lx` 的
`request/on/send/env/utils.buffer`，然后直接加载任意 LX 音源 `.js`。

但这个方案有三个硬伤：

1. **LX 插件不含搜索**。搜索、专辑、歌手、歌单还得我们自己写，
   省下来的只有「取流」这一小段。
2. **脚本质量不可控**。混淆、内置密钥、随时改地址、甚至可能读写本地文件
   （需要沙箱），维护成本会转嫁给我们。
3. **体积与构建**。多一个 JS 引擎，macOS/Windows 双平台构建和加固都要重测。

只有在「P0–P3 都做完、仍然觉得平台不够」时才值得考虑。

## 6. 风险与合规

| 风险 | 说明 | 应对 |
|---|---|---|
| 第三方接口变更 | 网易/GDAPI 都是非公开接口，随时可能改参数或封禁 | provider 隔离、快速失败、可关配置；基线和健康检查持续跑 |
| 版权/ToS | 项目定位是「匿名公开接口」，不应内置付费内容破解 | 不内置任何私有密钥；cookie 由用户自己提供；P3 网关由用户自备并自担责任 |
| 匹配串歌 | 兜底命中错版本（Live / 翻唱 / 伴奏） | 时长阈值 + 专辑加分 + 高置信才用 + UI 标注来源 |
| 网络环境 | 墙内访问部分第三方域名不稳 | 多源池 + 超时缩短 + 快速失败 |
| 缓存失效 | CDN 链接可能提前失效 | 失败清缓存重取；把 `expires_at` 纳入缓存键 |

## 7. 实施顺序与验收

```text
第 1 步  P0（1–2 天）         → 建 50 首基线，记录成功率/误判/音质准确率
第 2 步  P1 网易云（3–5 天）  → 搜索页双平台，取流成功率按平台分别统计
第 3 步  P2 兜底（1–2 天）    → 只看「酷我失败」子集的补位成功率
第 4 步  P3 网关（2–3 天）    → 可选，按需
```

验收指标：

| 指标 | 现状 | 目标 |
|---|---|---|
| 热门曲取流成功率（320k） | 24/24 = 100% | 保持 ≥ 99% |
| 长尾/翻唱曲取流成功率 | 未测 | 相对提升 ≥ 15pp |
| 片段误判率 | 存在（时长校验失效） | 0 |
| 音质标注准确率 | 存在失真 | 100% |
| 首次失败后的可恢复比例 | 0（直接判死） | ≥ 50% |

建议先只做 P0，用同一套 50 首样本对比前后数据，再决定 P1 值不值得投入。
P0 是纯工程改动，不引入任何新的第三方依赖，风险和成本都最低。

## 附：为什么不直接「把星海接进来」

| 维度 | 星海（LX 插件） | TinyMusic 需要 |
|---|---|---|
| 运行环境 | `globalThis.lx` 宿主 | Rust 进程内 provider |
| 提供的能力 | 只有 `musicUrl` / `lyric` / `pic` | 搜索、详情、专辑、歌手、歌单、下载 |
| 搜索结果来源 | LX 客户端内置 | 必须自己实现 |
| 凭据 | 私有后端 token / ChKSz apikey | 不内置私有密钥 |
| 稳定性 | 依赖 4 条第三方链路 | 需要可降级、可观测 |

所以答案不是「能不能装」，而是「**要不要把它的取址策略和候选后端，翻译成我们自己的 provider**」。
这个翻译工作，就是上面的 P1 + P2 + P3。
